# Status Review: L337 Audio Server + Player Client Integration

## Context
Goal: make the Rust `l337-audio-server` the **main audio output** for the `l337-player` Python client,
**including cross-device playback** (client and server on separate machines over LAN or WWAN). Both repos
are further along than the PLAN.md files suggest (the PLANs describe greenfield generation, but real code
already exists in both). This document reports actual status, reconciles the two sides, and plans the
changes for client-push streaming (direct + transcoded), a configurable least-played cache, and TLS+token
security.

---

## 1. Server status (`l337-audio-server`) — IMPLEMENTED, NOT VALIDATED

The Rust server is substantially built and matches PLAN.md closely:

| PLAN requirement | Status | Notes |
|---|---|---|
| Axum + Tokio REST on :1337 | DONE | `src/main.rs` wires all 9 routes |
| `Track`/`SpeedPayload`/`PoolSettings`/`PlayerStatus` models | DONE | `src/api/models.rs` |
| `current/next/prev.stream` active slots | DONE | `storage.rs::get_active_slot_path` |
| Persistent LRU pool keyed by `track_id` | DONE | `storage.rs` manifest + eviction |
| `precache_next/prev`, `trigger_next/previous` | DONE | `engine.rs` |
| Rodio `set_speed`, `set_volume` | DONE | `engine.rs` |
| LRU eviction w/ active-slot protection | DONE | `evict_if_needed` skips current/next/prev |
| GitHub Actions multi-OS build | PARTIAL | `.github/workflows` exists (not re-checked) |
| Crates | NOTE | `symphonia-vorbis` used (PLAN said `-ogg`/`-opus`); `reqwest` added for download |

**Gaps / risks on server side:**
1. **No seek endpoint.** `Player`/`APIPlayer` already have a no-op `seek_async`. Rust has no `/player/seek`.
2. **Status shape mismatch with client UI.** Server returns `{state, volume, speed, current_track, disk_pool_utilization_bytes, next_cached, prev_cached}`. Client UI (`core_tui.update_playback_progress`) additionally expects `state` to be **lowercase** (`playing`/`paused`/`stopped`) and a `time` field (`"cur:tot"`) for the progress bar. Server emits uppercase enum + no `time`. So progress/seek UI is broken against the Rust server.
3. **`stream_url` decoding depends on `reqwest`.** Fine on desktop; on Android the PLAN wants pure-Rust — `reqwest` uses system TLS, may need `rustls` feature.
4. **`unsafe impl Send/Sync for SendableEngine`** — fragile; `rodio::Sink` is `Send+Sync` so this can likely be removed. Not a blocker.
5. **No graceful volume endpoint** (`PlayerStatus` has volume but no `/player/volume` route).
6. Build not re-verified in this review (read-only). `edition = "2024"` + pinned crates imply a recent toolchain.

---

## 2. Client status (`l337-player`) — API scaffolding DONE, RUST NOT WIRED AS PRIMARY

The client already has a full API-only architecture (further than PLAN-client.md implies):

- `src/client/core/api_client.py` — `APIClient` (urllib-based) with all endpoints.
- `src/client/core/player.py` — `Player` is now **API-only** (delegates to `APIClient`).
- `src/client/core/api_player.py` — alternative `APIPlayer` (redundant with `player.py` now).
- `src/client/plugins/audio_server/fallback.py` — aiohttp server implementing the same API on top of
  ffplay/mpd/mpv. This is what runs today when `use_api=True`.
- `src/client/plugins/audio_server/dummy.py` — no-op test server.
- `core_tui.py` starts the **fallback** plugin automatically when `use_api=True`.

**The critical problem:** there is **no path to use the external Rust server**. The client only knows how to
launch the *fallback* or *dummy* plugins locally. There is no "connect to an already-running Rust server on
:1337" mode. Today `use_api=True` => runs fallback (mpv/ffplay), NOT the Rust engine.

---

## 3. Contract mismatches between client and server (MUST FIX)

These are the concrete reasons the server can't yet be the main output:

| # | Field / Behavior | Client sends / expects | Server expects / returns | Fix |
|---|---|---|---|---|
| C1 | Track payload | `track_id`? **NOT set**; url in `url` / `url_cached` | `Track{track_id, stream_url, ...}` — both required | Client must populate `track_id` (hash) + `stream_url` before POST `/player/play` & cache calls |
| C2 | State string case | lowercase `playing/paused/stopped` | uppercase `Playing/Paused/Stopped` | Agree one form. Recommend server serializes lowercase (client already lowercases in UI) |
| C3 | Progress/seek | `status['time'] = "cur:tot"` | none provided | Add `position_sec`/`duration_sec` to `PlayerStatus`; add `/player/seek` (POST `{position:u64}`) |
| C4 | Volume | no endpoint used | `PlayerStatus.volume` only | Add `/player/volume` (POST `{volume:f32}`) if UI exposes volume |
| C5 | `cache/next` semantics | client calls `play_next` => `cache_next` | server writes `next.stream` (good) | OK once C1 fixed; ensure caller passes real `stream_url` |
| C6 | `cache/previous` | client `append` => `cache_previous` | server writes `prev.stream` | OK once C1 fixed |
| C7 | `track_id` uniqueness | must be stable hash of source | server uses it as cache filename + eviction key | Client must generate deterministic `track_id` (e.g. sha1 of canonical url) |

---

## 4. What must change to make Rust the MAIN output

### Server changes (`l337-audio-server`)
1. **Add `/player/seek`** (POST `{position: u64}`) using `Sink::seek` / rodio `Seek` — needed for UI progress scrubbing.
2. **Add `/player/volume`** (POST `{volume: f32}`) if client UI controls volume (optional now).
3. **Expose playback position + duration** in `PlayerStatus` (`position_sec`, `duration_sec`); rods `Sink::get_pos` / decoder duration. Drives the progress bar.
4. **Serialize `state` lowercase** (or add `serde rename`) to match client UI, OR change client to uppercase. Recommend lowercase server-side for least client churn.
5. **Harden `track_id`/URL handling**: reject play/cache when `stream_url` empty with 400; treat missing `track_id` as 400 (do not synthesize).
6. **Android TLS**: switch `reqwest` to `rustls-tls` (pure-Rust) to satisfy PLAN's no-C-dep rule; verify CI.
7. (Optional) Drop the `unsafe impl Send/Sync` if `Sink` proves `Send+Sync`.

### Client changes (`l337-player`)
1. **New "external Rust server" mode**: add setting `audio_server = "rust"` (or auto-detect by probing `GET /player/status` on :1337 before launching fallback). When Rust is reachable, use `APIClient` directly against `http://localhost:1337` and **do NOT** start the fallback plugin.
2. **Populate `track_id` + `stream_url`** in `Player.play_async`/`play_next_async`/`append_async` before sending:
   - `track_id = sha1(canonical_stream_url or source_url)`
   - `stream_url = track['url_cached'] or track['url']`
   Keep `url`/`url_cached` for fallback compatibility.
3. **Normalize `state`** from status (handle both cases) so UI works against either server.
4. **Map new status fields**: read `position_sec`/`duration_sec` (fallback to `time` when present) for the progress bar; show `disk_pool_utilization_bytes` somewhere (settings/status panel).
5. **Implement `seek_async`** -> `POST /player/seek` when server supports it (fallback: best-effort / ignore).
6. **Remove/merge `api_player.py`** (duplicate of `player.py` API-only) to avoid drift.
7. **Make fallback plugin tolerant**: it currently reads `url`/`url_cached`; keep that, but also accept `stream_url`/`track_id` so both servers share one contract.

### Shared contract (document in both repos)
- Payload: `{track_id:str, stream_url:str, title?, artist?, duration?}`
- `state`: lowercase `playing|paused|stopped`
- `PlayerStatus`: add `position_sec`, `duration_sec`; keep `next_cached`, `prev_cached`, `disk_pool_utilization_bytes`, `volume`, `speed`, `current_track`.

---

## 5. Integration sequencing (recommended)
1. Server: add seek/volume + position/duration to status; lowercase state; 400 on bad payload. (Server-side, no client break.)
2. Client: generate `track_id`/`stream_url`; add "connect to external Rust" detection + mode; normalize status; implement seek.
3. Client: keep fallback plugin as secondary (when Rust not on :1337), now speaking the same `stream_url`/`track_id` contract.
4. Validate end-to-end: client in "rust" mode plays/caches/next/prev/seek/pause/speed against the Rust binary.

---

## 6. Decisions (confirmed with user)
- **`l337-audio-server` is itself a client audio-server PLUGIN**, on equal footing with `fallback`/`dummy`.
  Register it as `audio_server_l337` (or similar) in the plugin registry, implementing the same
  `BasePlugin` audio-server interface (`get_api_endpoint`, `start`, `stop`, `is_running`).
  - This plugin does NOT spawn a server; it only **probes** `http://localhost:1337/player/status`.
    If reachable, `get_api_endpoint()` returns `http://localhost:1337` and the client's `APIClient`
    talks directly to the user-managed Rust binary.
  - In **auto-detect mode**, `l337-audio-server` has the **highest priority** (before fallback/dummy).
    If :1337 is unavailable, fall through to `fallback`, then `dummy`.
  - User may also explicitly select it via `audio_server = l337-audio-server` in settings.
- **Volume control: add now.** Server gets `POST /player/volume {volume:f32}`; client volume UI calls it.

## 7. Revised integration plan

### Server (`l337-audio-server`)
1. Add `POST /player/volume` -> `engine.set_volume(f32)` (clamp 0.0..1.0).
2. Add `POST /player/seek` -> `Sink` seek to `position` secs (expose on `PlayerEngine`).
3. `PlayerStatus`: add `position_sec: Option<u64>`, `duration_sec: Option<u64>`.
   Populate from rodio `Sink::get_pos()` + decoded source duration.
4. Serialize `state` lowercase (`playing|paused|stopped`) — client UI already lowercases.
5. `play`/`cache_*` return `400` when `stream_url` or `track_id` missing/empty (no silent synthesize).
6. `reqwest` -> `rustls-tls` feature for Android pure-Rust build; verify CI.
7. (Optional) remove `unsafe impl Send/Sync` if `Sink` is `Send+Sync`.

### Client (`l337-player`)
1. **New plugin** `src/client/plugins/audio_server/l337.py`:
   - `L337AudioServerPlugin(BasePlugin)`: `start()` probes `GET /player/status` on :1337;
     `get_api_endpoint()` returns `http://localhost:1337` only if reachable; `stop()` is a no-op
     (does not kill the external binary).
   - Register in `registry.py` as `audio_server_l337`; add to `AUDIO_SERVER_OPTIONS`.
2. **Auto-detect priority**: reorder so `l337` is tried first, then `fallback`, then `dummy`.
   Update `core_tui._start_audio_server_plugin` + `audio_servers.detect_available_backends`.
3. **Client payload normalization**: in `Player.play_async/play_next_async/append_async`, set
   `track_id = sha1(canonical stream_url)` and `stream_url = track['url_cached'] or track['url']`

4. **Status normalization**: handle both `state` casings; read `position_sec`/`duration_sec`
   (fall back to `time` for local backends); surface `disk_pool_utilization_bytes`.
5. **Volume**: route volume control to `POST /player/volume` (best-effort on fallback/dummy).
6. **Seek**: `seek_async` -> `POST /player/seek` when supported.
7. Remove duplicate `api_player.py` (superseded by `player.py` API-only).

### Shared contract (document in both repos)
- Payload: `{track_id:str, stream_url:str, title?, artist?, duration?}`
- `state`: lowercase `playing|paused|stopped`

## 8. Cross-device streaming (LOCAL-FILE + REMOTE)
**Finding:** The server can ONLY ingest audio via `reqwest::get(stream_url)` (network `http(s)` GET,
`engine.rs:169`). `Track.stream_url` is a plain `String` (`models.rs:4`). There is **no** support for
local files the server cannot reach, and **no** `file://` or raw-upload path. So a file visible to the
client but not the server **cannot be played today**, and the design is localhost-only.

**Requirement (confirmed):** support running client and server on **separate devices** (LAN *and* WWAN).
The client must be able to deliver audio to the server either by (a) **direct file push**, or
(b) **client-side transcoding** (to cut bandwidth) — transcoding applies to local files, or whenever the
server machine lacks `yt-dlp`/network egress. A new configurable **`max_cache_size`** (default **256 MB**)
governs a persistent cache at `~/.cache/l337/l337-audio-server/cache/` that is evicted by **least-played /
LRU** using a play-count record.

### 8.1 Server changes
1. **Config-driven cache root + size.** Replace the hardcoded `500MB` and `dirs::cache_dir()/l337player`
   with `~/.cache/l337/l337-audio-server/cache/` and a `max_cache_size` from `config.toml`
   (`[storage] max_cache_size_bytes`, default 256 MiB). `StorageManager::new` reads it.
2. **Streaming upload endpoints.** Add `POST /player/play/stream`, `POST /player/cache/next/stream`,
   `POST /player/cache/previous/stream`. Each accepts a **raw/streaming body** (axum `Body` /
   `StreamBody` consumer) plus identity via header `X-Track-Id` (and optional `X-Title`/`X-Artist`).
   Writes chunks straight to `current/next/prev.stream` (bypassing `reqwest`). Evict-then-write so the
   incoming stream never exceeds `max_cache_size`.
3. **Play-count records (already partially present).** `CacheManifestEntry` already has `play_count` +
   `last_accessed` (`models.rs:42`). Promotes `update_access` on every play; eviction orders by
   **least-played then oldest** (`sort_by_key(play_count, last_accessed)`).
4. **`file://` passthrough** (same-device convenience): in `download_stream`, if `stream_url` starts with
   `file://` or is an absolute path the server can read, copy via `tokio::fs` instead of `reqwest`.
5. **No server-side transcoding.** Server remains a pure sink; transcoding is the client's job (keeps the
   Rust binary dependency-free per PLAN).

### 8.2 Client changes
1. **Source classification in `Player`.** In `play_async/play_next_async/append_async`, decide the
   delivery mode:
   - Network `http(s)` URL the server *can* fetch → send `{stream_url}` as today (server downloads).
   - **Local file** (`local_file`/`file://`) OR server can't fetch → **push**.
2. **Push transport = HTTP streaming.** Extend `APIClient` to stream the file in chunks
   (`requests`/ `httpx` with `data=fileobj`, or `urllib` with a file wrapper) to the `*/stream` endpoint,
   setting `X-Track-Id` = `track_id`. Supports both same-device and cross-device.
3. **Transcoding (config-gated).** When the user enables `transcode` *and* the source is local / server
   lacks egress, run `ffmpeg`/`yt-dlp --extract-audio` to a temp file (opus/mp3 per
   `music_download_format`/`bitrate`) and stream **that** to the server. Reuse existing transcode settings
   in `settings.py` (`transcode`, `music_download_format`, `music_download_bitrate`). If transcoding
   disabled, push the raw file.
4. **New settings** (in `settings.py` defaults): `server_url` (default `http://localhost:1337`),
   `server_token` (shared secret), `max_cache_size_mb` (informational; server owns the real value),
   `remote_transcode` (`True`/`False`).

## 9. Security: TLS + shared token (LAN & WWAN)
**Requirement (confirmed):** secure enough for **both LAN and WWAN (mobile)**. Approach: **built-in TLS
(HTTPS)** on the server + a **shared token** established once by the user (server prints token at first
run / in config; client enters it in settings).

### 9.1 Server
1. **TLS termination.** Use `axum` + `rustls` (or `hyper-tls`/ `tokio-rustls`). On startup, load
   `config.toml` `[server] tls_cert` + `tls_key`; if absent, **auto-generate a self-signed cert** into
   the config dir on first run and log the fingerprint. Listen on the configured `host` (allow `0.0.0.0`
   for LAN/WWAN) + `port` (1337).
2. **Token auth middleware.** Every request (except `GET /health`) must carry header
   `Authorization: Bearer <token>` (or `X-L337-Token`). Reject `401` otherwise. Token sourced from
   `[server] token` in `config.toml`; if unset, generate a random token at first run, persist it, and log
   it for the user to copy into the client.
3. **`GET /health`** lightweight unauthenticated liveness probe (used by the client `l337` plugin to
   detect reachability without leaking state).

### 9.2 Client
1. **`APIClient` → HTTPS + token.** Switch transport to `httpx` (or `urllib` + `ssl`) with `verify`
   (allow self-signed via fingerprint option) and attach the bearer token from `server_token`.
2. **`l337` audio-server plugin** (`audio_server_l337`) probes `GET {server_url}/health`; if reachable
   and token-accepted, `get_api_endpoint()` returns `server_url`. Highest auto-detect priority.
3. **Token entry in settings UI** (settings_tui) + new `server_url` field.

## 10. Sequencing
1. Server: config cache root/size (§8.1.1) + play-count eviction (§8.1.3) + `file://` passthrough (§8.1.4).
2. Server: streaming `*/stream` upload endpoints (§8.1.2).
3. Server: TLS + token middleware + `/health` (§9.1).
4. Client: `APIClient` HTTPS+token; `server_url`/`server_token` settings (§9.2).
5. Client: `l337` plugin (probe-only, highest priority) (§7 + §9.2).
6. Client: source classification + streaming push + config-gated transcode (§8.2).
7. Client: payload normalization (`track_id`/`stream_url`), status normalization, seek/volume (§5/§7).
8. E2E: localhost (fallback avoided, Rust primary) → LAN (separate device, TLS+token) → WWAN.
1. Server: volume + seek + status position/duration + lowercase state + 400 validation.
2. Client: `l337` plugin (probe-only) + auto-detect priority + payload normalization + status/seek/volume mapping.
3. Keep `fallback`/`dummy` speaking the same `stream_url`/`track_id` contract.
4. E2E: client in auto-detect/runtime finds Rust on :1337, drives play/cache/next/prev/seek/pause/speed/volume.
