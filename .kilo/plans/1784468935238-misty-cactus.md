# Plan: PipeWire-Native Audio Backend + Commit Untracked Files

## Context
The server currently uses `rodio` (`DeviceSinkBuilder::open_default_sink()`), which on Linux defaults to ALSA. This means the app does not appear in the PipeWire mixer and system volume controls are ignored. We need a PipeWire-native output so the server behaves like a modern desktop audio client.

## Phase 0 — Commit untracked source files
- `git add` the following untracked paths (exclude `target/` — it is build output and already gitignored):
  - `.kilo/` (Kilo config + plans)
  - `AGENTS.md`
  - `plugins/` and `plugins/src/` (cross-platform plugin stubs)
  - `src/plugins/` (plugin loader + trait definitions)
- Commit with a message that reflects the staged content, e.g. `chore: add plugin scaffolding and kilo config`

## Phase 1 — Replace rodio with cpal (PipeWire-native I/O)
**Why cpal:** `cpal` 0.15+ creates native PipeWire streams on PipeWire systems. This makes the server appear in `pactl`/`pw-cli` and respond to desktop volume keys.

### Cargo.toml changes
- Remove `rodio` dependency.
- Add `cpal = "0.15"` (or latest 0.15.x that supports edition 2024).
- Add `symphonia = { version = "0.5", features = ["mp3", "mp4", "flac", "vorbis", "wav"] }` for decoding (rodio used symphonia under the hood; we take over decode + cpal handles I/O).

### src/player/engine.rs rewrite
Replace `rodio::Player`, `Mixer`, `MixerDeviceSink` with a cpal-based playback stream:

- **Struct changes:**
  - Remove `player: Option<Player>`, `mixer: Option<Mixer>`, `_device_sink: Option<MixerDeviceSink>`.
  - Add `stream: Option<cpal::Stream>` and `sample_format: SampleFormat` (track what cpal gives us).
  - Keep `volume: f32`, `speed: f32`, `state`, `current_track`, `duration_sec`.

- **Audio output init (main.rs -> engine.rs):**
  - Call `cpal::default_output_device()`.
  - Build a `cpal::Stream` with a write callback that pulls decoded samples from a shared `Arc<Mutex<AudioBuffer>>` (ring buffer or simple Vec with read/write indices).
  - Volume is applied in software inside the write callback (scales f32 samples). On PipeWire, the stream will still appear as a native client; desktop volume keys control the PipeWire node, but software volume gives the server its own independent gain.
  - Speed is applied by adjusting the read stride / resampling in the callback, or by tracking playback position manually.

- **Playback flow:**
  1. Download / load file into memory (keep existing `load_file_to_bytes` pattern).
  2. Decode with `symphonia` to a `Vec<f32>` (PCM).
  3. Push PCM into the shared audio buffer.
  4. The cpal write callback drains the buffer to the device.
  5. Track position by counting samples written.

- **Control methods:**
  - `play()`: start/resume the stream, set state to Playing.
  - `pause()`: drop the stream or silence the callback, set state to Paused.
  - `stop()`: drop the stream, clear the buffer, reset position, set state to Stopped.
  - `seek(pos_sec)`: decode again from the requested offset into a fresh PCM buffer, swap it in.
  - `set_volume(vol)`: clamp and store; callback applies it each sample.
  - `set_speed(speed)`: store; adjust read-ahead/stride in callback.

- **Status / position:**
  - `position_sec` = samples_written / sample_rate.
  - `duration_sec` = total PCM samples / sample_rate (computed at decode time).

### src/main.rs changes
- Remove `use rodio::DeviceSinkBuilder;`.
- Remove `device_sink` / `mixer` local variables.
- Initialize engine with just `storage`; engine constructs its own cpal stream lazily or in `new()`.
- Keep the `--dummy` flag behavior: if set, skip cpal init and store `stream: None`.

## Phase 2 — systemd PipeWire per-user session (Option C: l337 system user)
The `l337` system user is retained for strongest isolation on an internet-exposed host. PipeWire does not need the `audio` group; it mediates device access via socket. We start a dedicated per-user PipeWire instance for `l337` inside the systemd unit.

### install-systemd.sh changes
- **Keep:** `User=l337`, `Group=l337`, `ProtectSystem=strict`, etc.
- **Remove:** `usermod -aG audio "$USER_NAME"` — no longer needed with PipeWire.
- **Add to `[Service]`:**
  - `Environment=XDG_RUNTIME_DIR=/run/user/UID` where UID is the `l337` user's numeric UID (looked up at install time).
  - `ExecStartPre=/usr/bin/pipewire` (or a small wrapper script at `/opt/l337-audio-server/scripts/start-pipewire.sh` that exports `XDG_RUNTIME_DIR` then execs `pipewire`).
  - Optional: `ExecStartPre=/usr/bin/wireplumber` if the host uses WirePlumber as the session manager (most modern distros do).
  - `Restart=on-failure` applies to the main server; `ExecStartPre` services are not auto-restarted by default. If PipeWire crashes, the server will fail to open a device and exit; systemd will restart the server, which in turn re-runs `ExecStartPre`.
- **Verification output:** After install, print a note telling the operator to run `sudo -u l337 pactl list sinks` or `sudo -u l337 pw-cli ls Node` to confirm the PipeWire node appears.

### src/main.rs changes
- Detect PipeWire at runtime: if `PIPEWIRE_REMOTE` or `XDG_RUNTIME_DIR` points to a running session, cpal will open a PipeWire stream automatically. No code change needed beyond the cpal swap (cpal probes the session via the standard env/XDG paths).
- Keep the `--dummy` flag behavior: if set, skip cpal init and store `stream: None`.

## Phase 3 — Validation
- `cargo check` / `cargo build` after dependency swap.
- Start service, confirm `pactl list short sinks` (or `pw-cli ls Node`) shows a node owned by `l337-audio-server`.
- Confirm desktop volume keys adjust the server's sink in `pavucontrol` / PipeWire mixer.
- Confirm `GET /player/status` reports correct `position_sec` and `state`.

## Tradeoffs / Questions
1. **Volume semantics:** Desktop volume keys will control the PipeWire node, while the API's `/player/volume` applies software gain. Is this acceptable, or should the API volume be removed in favor of letting PipeWire be the single source of truth?
2. **Speed / pitch:** Real-time playback-speed with pitch preservation requires a resampler. A simple stride-based approach changes pitch. Do we want to pull in `rubato` or `samplerate` for high-quality resampling, or keep it simple (speed affects pitch) for now?
3. **User vs system service:** If the host is a desktop, running as the active desktop user (user service) gives seamless PipeWire access. If it's a headless server, we may need a different approach (e.g., `PIPEWIRE_SYSTEM` or a dedicated system-wide PipeWire instance).
